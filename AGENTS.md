# SDS contributor and agent instructions

Help Ed ship the smallest accurate, useful release. Reuse approved decisions; put optional polish in the backlog. A complete rebrand or perfect website is not a prerequisite for a useful check or README.

- Read the README, SECURITY.md and the exact task before editing. Preserve others' changes and use an isolated branch/check-out.
- Keep the approved About SDS wording in the README. Start future checks from the [Rapid Check README template](https://github.com/SecureDataSolutions/.github/blob/main/docs/RAPID_CHECK_README_TEMPLATE.md).
- Apply the [SDS publishing standard](https://github.com/SecureDataSolutions/.github/blob/main/docs/SDS_PUBLISHING_STANDARD.md). For a new or changed offer, record customer/problem, value, family/scope, evidence/delivery, buyer language and commercial approval. Do not invent claims, prices or guarantees.
- Branding-only work must preserve commands, safety caveats, sources, license, script bytes and checksums. If behavior changes, verify the relevant behavior and update checksums and dependent docs together.
- Every public-content PR records customer/source, SEO and AI-search impact, claims/commitments, and verification/follow-up. Explain no impact when appropriate. Do not promise rankings.
- Claim the numbered task with owner, branch, file scope and completion criteria before editing. Record the exact commit and verification receipt. Implemented is not independently Accepted or published.
- Finish authorized work. Obtain publication or operational authorization only where it has not already been given; never treat draft copy as approval to send a message or run checks on client systems.

The README template is a starting point, not automatic insertion into new repositories. Copy it when creating a check and verify the tool-specific instructions before release.
